# BUG-2026-11-16T17:45:54: Idle CPU 80–93% from unconditional vblank re-render timer

## Problem

eswm uses 80–93% CPU while idle (no client windows, no input), RSS 287 MB. Hyprland idles at 0% CPU / 84 MB RSS. The compositor renders continuously at ~60fps with nothing changing.

Actual behavior: eswm burns one core even on a bare idle desktop.
Expected behavior: eswm should render at ~0% CPU when nothing has changed.

How to reproduce: start eswm on a bare TTY with no clients, observe CPU staying pegged at 80–93%.

## Root Cause Analysis

Prior bug BUG-2026-11-16T17:30:00 reported identical symptoms (~55% idle CPU) and was marked open. Its fix throttled frame callbacks to ~30fps, but frame callbacks are not what drives the render loop; they only notify clients that a frame completed. Throttling callbacks does not stop eswm from rendering.

The actual render loop is driven by `frame_finish` in the udev/DRM backend. After every successful `queue_frame`, `frame_finish` unconditionally sets `schedule_render = true` and registers a calloop timer to call `data.render()` again after ~60% of a frame duration (~10ms at 60Hz). This creates a continuous render loop at refresh rate regardless of whether anything changed.

The main event loop in `run_udev` does check `redraw_needed` and skips idle page-flips, but `frame_finish` bypasses that gate entirely; it calls `state.render()` directly from a timer callback without consulting `redraw_needed`. So even with `redraw_needed = false`, the vblank timer keeps firing `render()` -> `render_surface()` -> `queue_frame()` -> `frame_finish()` -> next timer, forever.

Prior fix assessment: recurrence of the same symptom class (idle CPU), but a different root cause. The frame callback throttle treated the symptom (client commit loop) not the disease (compositor self-driving render loop).

Risk level: Low. No security exploit path; this is a performance/resource bug.

## Resolution

Fixed via extracted helper `render_timer_delay(redraw_needed, frame_duration) -> Option<Duration>` in src/udev.rs. `frame_finish` skips scheduling the vblank re-render timer when `redraw_needed` is false, and the timer callback re-checks + consumes the flag before rendering, so the loop can no longer feed itself. Commits: 5dd7c7f (test, RED) → d9c47f9 (fix, GREEN). 58/58 tests, clippy, build all green. Verified on DRM backend via /proc CPU sampling: ~0% CPU for first 10s idle; a burst at t=12s correlated with external activity (user interaction).
